# Full end-to-end test suite for `scripts/°base/git/split.py` / `get-base.py`

## Context

`scripts/°base/git/°split_lib/` keeps three branch variants in sync for any feature branch adopted into a repo built on this `base`: a `{branch}` clean branch (no AI/base content, safe to publish), an `ai/UNCLEAN/{branch}` working branch (code + AI content mixed freely), and an `ai/history/{branch}` branch (AI-only leftovers) — plus a repo-wide `ai/history/{main}` ("history-master") that replays merged branches' AI history and periodically folds an upstream `base/base` template remote. Every module (`cli.py`, `branches.py`, `classify.py`, `git_ops.py`, `history_master.py`, `rebase_to_master.py`, `sync_splits.py`, `sync_unclean.py`, `trailers.py`, `bootstrap.py`, `recovery.py`, `push_checks.py`) already has thorough *unit*-level test coverage in `scripts/°base/tests/test_git_split_*.py`, but nothing exercises the tool end-to-end the way a real adopting repo would: preparing a repo with a realistic mix of history shapes, checking out realistic branch states, and running the actual `get-base.py`/`split.py` entry points against them.

This plan adds that missing end-to-end layer, plus a small real feature gap it surfaces: `history_master.py`'s first-time `base/base` fold has no auto-conflict-resolution (unlike *recreating* an already-resolved fold, which does), so a repo that already committed its own `README.md`/`.gitignore` before ever folding `base/base` would hit a manual conflict on those two predictable, expected-to-differ files. We're closing that gap as part of this work, confirmed with the user (they want first-time conflicts on exactly these two paths to auto-resolve, not just recreated ones).

Two clarifications resolved with the user before finalizing this plan:
- Repo variant 1.6 needs a *second, genuinely different* `base/base` merge (git's real `--no-ff` behavior is a no-op on an already-merged ref) — solved by using two different commits from this repo's own `base` branch, resolved **dynamically at test-run time** rather than hardcoded: "now" (`base`'s current tip) and "now-2" (`base`'s tip two first-parent commits earlier). No pinned constants to maintain — whatever `base` currently looks like when the test runs, the fixture always has two genuinely distinct, real commits to merge in sequence.
- The step-11 "except 2.9" rebase clause is just the general, always-true dependency rule (unclean rebases onto history's just-rebased tip; history-master itself is advanced via `update-history-master`, not `rebase-branches-to-master`) — no extra 7th deep-flow case is needed; the standard per-repo-variant deep flow already covers it via the explicit two-call sequence.

One correction I made to the design that came out of the Plan-agent draft: repo-variant 5/6's `base/base` merges are done as **plain `git merge --no-ff`** during test-fixture *preparation* (`is_allowed_merge: true`), not by running `split.py` — so they never carry an `X-Base-History-Merge-Kind` trailer (only merges `_fold_base`/`recreate_base_merge` themselves perform get that trailer). Step 7's "no *new* base/base merge on `feature/test-eins`" check therefore can't be a trailer lookup.

Instead it uses two much simpler checks, relying on a fact already established elsewhere in this plan: `sync-splits` (the code path `feature/test-eins` is generated by) *never creates a merge commit at all* — it only ever cherry-picks single-parent commits (`make_split_commit`) onto a clean branch that starts life as a plain branch-off of `mane`'s tip. So:
  1. **Which shas are the base merges is already known** — we recorded them ourselves while building the repo variant (each `CommitRecord` with `merge.branch == "base/base"` in the manifest). Assert each of those shas is still an ancestor of `feature/test-eins` (`git_ops.is_ancestor(sha, feature_test_eins_tip, cwd)`) — confirms they're inherited from `mane`, not lost.
  2. **No new merge (of any kind) got added** — assert `git rev-list --merges --count feature/test-eins` equals `git rev-list --merges --count mane` (captured right when `feature/test-eins` is created, before `mane` advances again in step 9). Since `sync-splits` cherry-picks only, this count can only change if something merged — so an unchanged count is direct proof no new base/base merge (or any other merge) was introduced. This subsumes the trailer-based idea entirely and needs no "does this merge trace into base's history" logic at all.

## Part 1 — `history_master.py`: auto-resolve `README.md`/`.gitignore` on first-time base fold

### Change

In `scripts/°base/git/°split_lib/history_master.py`, add near the other module constants (~line 35):

```python
# Paths auto-resolved (in favor of base_sha's content) when a first-time
# base/base fold conflicts on them -- see _fold_base(). Top-level, exact
# match only.
FIRST_FOLD_AUTO_RESOLVE_PATHS = ("README.md", ".gitignore")
```

Add a small helper right after `recreate_base_merge` (~line 389), mirroring its per-path blob-reuse mechanism but sourcing content from `base_sha` (the incoming tip) instead of a prior resolved merge, since a first-time fold has no prior resolution to reuse:

```python
def _auto_resolve_first_fold_conflicts(base_sha: str, conflicted: list[str], cwd: Path) -> set[str]:
    resolved: set[str] = set()
    for path in conflicted:
        if path not in FIRST_FOLD_AUTO_RESOLVE_PATHS:
            continue
        content = git_ops.show_path_at(base_sha, path, cwd)
        target = cwd / path
        target.parent.mkdir(parents=True, exist_ok=True)
        target.write_bytes(content)
        _git(["add", "--", path], cwd, check=True)
        resolved.add(path)
    return resolved
```

In `_fold_base` (~line 424-432), change the conflict branch so only *remaining* (non-auto-resolvable) conflicts raise:

```python
    result = _git(merge_args, cwd)
    if result.returncode != 0:
        conflicted = _conflicted_paths(cwd)
        if not conflicted:
            logger.debug("$ git merge --abort")
            git_ops.merge_abort(cwd)
            _cleanup_scratch(cwd)
            raise HistoryMasterError(f"merge of {base_sha} onto {onto} failed: {result.stderr}")
        auto_resolved = _auto_resolve_first_fold_conflicts(base_sha, conflicted, cwd)
        remaining = [path for path in conflicted if path not in auto_resolved]
        if remaining:
            raise MergeConflict(base_sha, onto, result.stderr)
    return _complete_base_fold(base_sha, cwd)
```

No other function needs to change: `_do_continue`'s existing pending-"merge" handling already just re-checks `_conflicted_paths(cwd)` and proceeds once empty, so a partially-auto-resolved-then-manually-finished conflict already works with zero changes there.

### Tests

Add to `scripts/°base/tests/test_git_split_history_master.py`, in `HistoryMasterTests`, right after `test_first_base_fold_allows_unrelated_histories`:

- `test_first_base_fold_auto_resolves_readme_and_gitignore`: seed `master` with its own `README.md`/`.gitignore` content, build a fresh unrelated `base` remote (`init_repo(..., branch="base")`, matching the existing unrelated-histories test's pattern) with *different* `README.md`/`.gitignore` content, fetch it, run `update_history_master(...)`, assert `status == "ok"`, `result["base_merge"]` is set, and `git_ops.show_path_at(result["history_master"], "README.md"/".gitignore", cwd)` both equal base's content (not master's).
- `test_first_base_fold_still_conflicts_on_other_paths_while_auto_resolving_readme`: same setup plus both sides also add a genuinely conflicting third file; assert `status == "conflict"`, that `README.md`/`.gitignore` are no longer listed by `git diff --name-only --diff-filter=U` (already auto-resolved and staged) while the third file still is, then resolve it by hand + `--continue` and assert the final README/.gitignore content is still base's.

## Part 1.5 — `sync_splits.py`: detect & handle a merge commit inside `ai/UNCLEAN/*`

### The bug this fixes

`sync_branch()`'s replay range (`commits_to_replay` → `git_ops.rev_list_reverse(f"{last_synced_source}..{unclean_ref}", cwd)`) is a **plain** `git rev-list A..B` — not `--first-parent`. If an unclean branch ever contains a merge commit (e.g. someone merges `base/base` straight into `ai/UNCLEAN/{branch}`, which is allowed there), this walks *every* commit reachable via the merge's second parent too — for a first-time `base/base` merge, that's potentially thousands of `base/base`'s own historical commits, each individually fed through `classify_commit`/`make_split_commit` as if it were an ordinary linear commit on this branch. Confirmed by reading `tree_ops.raw_diff_for_commit`: it already diffs any commit (merge or not) against only its *first* parent — so the walk, not the per-commit diff, is what's broken.

### Fix

1. Add `git_ops.parents_of(sha, cwd) -> list[str]` (`git rev-list --parents -n 1 <sha>`, drop the first token) and `git_ops.rev_list_first_parent_reverse(range_expr, cwd) -> list[str]` (`git rev-list --first-parent --reverse <range_expr>`) — promoting `history_master.py`'s existing private `_first_parent_chain_reverse` (history_master.py:122-141) to shared plumbing; have `history_master.py` call the shared version instead of keeping its own copy (small dedup, no behavior change there).
2. Change `commits_to_replay` (sync_splits.py:66-79) to use `git_ops.rev_list_first_parent_reverse` instead of `git_ops.rev_list_reverse` — this alone stops the ancestor-unrolling bug structurally, regardless of what happens next with the merge commit itself.
3. Add `class UncleanMergeDetected(RuntimeError)` (sha, parents) to `sync_splits.py`. In `sync_branch()`'s clean-pass and history-pass loops (sync_splits.py:200-222, 235-257), before calling `classify_commit`, check `git_ops.parents_of(source_sha, cwd)`; if more than one parent, raise `UncleanMergeDetected` instead of processing it as an ordinary commit.

### CLI-layer handling (`cli.py`)

Catch `UncleanMergeDetected` in the `sync-splits` dispatch and present the four choices exactly as specified:

- **(a) Fake it** — record the merge's own net diff against its first parent (i.e. exactly what `raw_diff_for_commit`/`build_filtered_tree` already compute for *any* commit) as one ordinary single-parent split commit, with the message noting it was originally a merge (both parent shas, real merge metadata) but landing as a flattened commit, not a real merge.
- **(b) Attempt a real merge** — actually merge the commit's second parent onto the current clean/history tip, auto-resolving `README.md`/`.gitignore` the same way as Part 1's fix (reuse `_auto_resolve_first_fold_conflicts`-style logic, or extract it to a shared spot both modules import). On any other conflict, abort that attempt and re-present the menu **without** option (b) (matches the spec: "failure returns to this question, without b)").
- **(c) User merges it themselves** — print the exact `git merge --no-ff <second-parent-sha>` command against the correct target ref, wait for Enter, then verify a real merge commit now exists there; if not, return to the menu.
- **(d) Abort** — print revert instructions (the ref hasn't moved yet at this point, so this is just informational) and stop.

Non-interactive runs (no tty, or `--yes`) have no safe default among a/b/c/d — error out clearly, pointing at a new explicit `--unclean-merge={fake,attempt,abort}` flag for non-interactive/CI use instead of guessing.

### Tests

Add to the *existing* `scripts/°base/tests/test_git_split_sync_splits.py` (not a new file): a test seeding `ai/UNCLEAN/{branch}` with a real merge commit (e.g. merging in a small unrelated local branch, not necessarily this repo's real `base` — keeps it fast/hermetic), asserting `sync_branch()` raises `UncleanMergeDetected` rather than unrolling/crashing, plus one test per resolution path (a/b/d — (c) needs a simulated `input()`/tty, cover it if time allows, otherwise note it as a manual/documented gap) confirming the resulting clean/history commit shape matches the chosen option. These stay separate from the e2e smoke/deep-flow suite below — merging `base/base` directly into an `ai/UNCLEAN/*` branch is **not** constructed in the Part 2/3 fixtures, since it needs the interactive menu rather than a scripted `--yes` run; flag this explicitly if broader e2e coverage of it is wanted later.

## Part 2 — Shared e2e fixture module

New file: `scripts/°base/tests/_git_split_e2e_fixtures.py`, imported by the new test files the same way existing files import `_git_test_helpers.py` (`sys.path.insert` + plain import), and itself importing `git`/`make_commit`/`init_repo` from `_git_test_helpers` plus `°split_lib.{git_ops,branches,classify,trailers}` via the same `LIB_ROOT` sys.path-insert pattern the other test files already use.

### Manifest schema

```python
@dataclass(frozen=True)
class MergeInfo:
    branch: str            # "empty/init" | "base/base"
    commit_theirs: str
    commit_ours: str
    is_allowed_merge: bool

@dataclass
class CommitRecord:
    commit: str
    merge: MergeInfo | None
    code: bool
    ai: bool
    msg: str
    trailer: str

Manifest = list[CommitRecord]
```

`record_commit(sha, *, merge, cwd) -> CommitRecord`: combines `git_ops.changed_paths_for_commit` + `classify.classify_commit` (for `code`/`ai`) + a message/trailer split. For the message/trailer split, reuse the same trailer-block-detection approach `sync_unclean.py` already uses internally (walk lines backward from the end while they match a `Key: value` shape) rather than a naive `rpartition("\n\n")` — "both" commits get real bodies, so a blank-line split alone is unreliable. If that logic isn't already exposed as a reusable function, add a small `trailers.split_trailer_block(message) -> tuple[str, str]` to `trailers.py` and have both `sync_unclean.py` and this fixture module call it, rather than duplicating the regex a third time.

### Fixture helpers

- `make_empty_init_remote(tmp_root) -> Path`: builds a tiny local one-commit repo (`init_repo(..., branch="init")` + one commit) as a hermetic, offline stand-in for the real `EmptyAAS/empty.git` remote.
- `resolve_this_repo_root() -> Path`: `git -C <this test file's dir> rev-parse --show-toplevel` — the actual on-disk repo running the tests (never a temp fixture).
- `add_and_fetch_real_base_branch(repo_root, *, pin_sha=None) -> str`: adds a `base` remote pointed at `resolve_this_repo_root()`, `git fetch base base`, and returns either `pin_sha` (verified reachable) or, if `pin_sha` is `None`, the freshly-fetched `refs/remotes/base/base` tip ("now").
- `resolve_base_sha_two_commits_earlier(repo_root) -> str`: after a fetch, resolves `git rev-parse refs/remotes/base/base~2` ("now-2") — the same branch's tip two first-parent commits back. No pinned/hardcoded shas anywhere: both "now" and "now-2" are resolved fresh against whatever `base`'s actual current history is at test-run time, so nothing needs manual bumping as this repo's own `base` branch keeps evolving.
- `run_fake_curl(repo_root, *args, this_repo_root=None) -> subprocess.CompletedProcess`: reads `scripts/°base/git/get-base.py`'s source text from `this_repo_root` and runs `subprocess.run([sys.executable, "-", *args], cwd=repo_root, input=script_text, capture_output=True, text=True)` — piping via stdin exactly like the documented `curl -fSL ... | python3 -` one-liner, no real network or HTTP server. Caller must have already pre-added a `base` remote on `repo_root` pointed locally, since `get-base.py`'s `ensure_base_remote()` never overwrites an existing remote but its `main()` unconditionally fetches `base` regardless of explicit argv.
- `assert_no_unresolved_merge_state(repo_root)`: asserts no `.git/MERGE_HEAD`, `.git/CHERRY_PICK_HEAD`, `.git/rebase-merge`, or `.git/rebase-apply`, and that `git status --porcelain` has no `U` (unmerged) entries — deliberately *not* a fully-clean-tree check, since `.rebase-recovery.tmp` is always left behind by a real run.
- `_random_commits(repo_root, manifest, n, *, code=True, ai=False, both=False)`: shared commit-generator used by every variant builder, appending `CommitRecord`s via `record_commit` as it goes, keeping manifest construction uniform.

- Variant 4 uses README.md's "Setup: a) Checkout" recipe (`git switch --create mane base/base`, at whatever `base/base`'s tip resolves to "now") — no merge commit, `mane` literally starts at base's tip.
- Variant 5 uses "Setup: c) Merge base/base" verbatim (`git merge --allow-unrelated-histories --no-verify empty/init`, then `git merge --no-ff --no-verify base/base` at "now"), recording both merges with `is_allowed_merge=True`.
